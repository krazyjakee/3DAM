Build status by capability phase

3DAM — Roadmap

Status: Draft v0.3 · Scope: build status and delivery strategy.

This page tracks build status against the capability phasing defined in PRODUCT_SPEC.md §9 — the single source of truth for what 3DAM builds and in what order. It layers progress notes and delivery detail on top of that phasing; it does not define a second, competing sequence.

An earlier version of this doc carried a parallel front-end build order with its own "stage" numbers running alongside the capability phases. That second axis was the source of confusion and has been removed. There is now one set of numbers — the capability phases below (from spec §9). Front-end work (web client, viewer islands, responsive pass, desktop GUI) is web-first and is referred to by name, never renumbered as separate stages — see Front-end sequence below.

See PRODUCT_SPEC.md for what 3DAM is, MISSION.md for why, and DESIGN_GUIDELINES.md for the rules.

Front-end sequence (web-first)

Two decisions shape the order of front-end work. Neither introduces a competing phase numbering — they sit inside the capability phases above.

  1. Web UI before the desktop GUI. Build the browser-based web client first, then the native egui desktop app. A web front end has a much faster iteration loop — hot reload, browser devtools, no native rebuild/repackage cycle — so the layout, interaction, and workflow settle against real libraries sooner. The desktop GUI follows, reusing the same engine and API.
  2. A hybrid web front end, not egui-in-WASM for everything. The web client is its own codebase — an ordinary React + CSS app served by 3dam serve — using WASM only where it is genuinely needed (the interactive 3D viewer and hot render paths like waveforms). Everything else — browse grid, search, tags, panels, navigation — is plain DOM, which gets responsive layout, touch, accessibility, and text input essentially for free.

Rationale and the frozen choices live in ADR 0008 (React + TypeScript + Tailwind) and ADR 0009 §9 (WASM-island packaging, WebGPU + WebGL2 fallback, each frontend owns its presentation, native desktop GUI — no webview), and in PRODUCT_SPEC.md §7. The front-end increments, named not numbered, are:

  • Engine + serve API core — 3dam-core behind a LibraryService boundary, exposed over the 3dam serve HTTP/WS API; the CLI rides the same API. (Part of phases 1 & 5.)
  • React web client — the three-region workspace (browse grid, search, facets, tags, previews) as DOM against the serve API; the admin Settings / Administration surface (feature flags, and later accounts) lands here too, cheap because it is DOM. (Serves phases 2 & 5.)
  • WASM viewer islands — the interactive 3D viewer and waveform render as focused wgpu components embedded in the DOM layout (the dam-viewer crate → web/src/islands/), not a full-page canvas. (Serves phase 2.)
  • Responsive + touch pass — the web client degrades gracefully to tablet/phone widths (see Mobile & tablet posture) before it is considered done.
  • Desktop GUI (egui) — the native app, reusing the settled interaction patterns and the same engine/API. (Phase 5 / spec §9 GUI parity.)

Progress

2026-07-06

Foundation — first vertical slice Shipped

The Cargo workspace exists (all crates scaffolded; packages named dam-*, binary 3dam — ADR 0010). Working end-to-end: the embedded engine (EmbeddedLibrary over a SQLite store, background scan job, cursor-paginated search + facets + stats), 3dam serve (axum HTTP/WS mirroring the LibraryService surface), and CLI parity (scan/search/sources/stats/get over either the embedded engine or a remote server via --connect — byte-identical results prove the seam holds).

2026-07-06

Web client, viewer islands, responsive pass — first cut Shipped

The browser front-end exists as a web/ codebase — React + TypeScript + Tailwind on Vite/pnpm (ADR 0008), the sole non-Rust codebase — talking to the engine purely over the serve API. It delivers the three-region workspace as DOM: Navigation (facets + sources + add-source), a virtualised grid⇄table Browser with search/sort/infinite-scroll and URL-driven view state, and an Inspector fed by get_asset. One /api/ws socket invalidates the affected caches so scans and new assets stream in live. 3dam serve embeds the built bundle (rust-embed over web/dist/) with SPA-fallback routing. The dam-viewer crate (wgpu 3D + waveform islands, WebGPU/WebGL2 via wasm-pack) and the responsive/touch collapse (single-column below lg with drawers, 44px touch targets) are built and the live viewer is wired into the Inspector.

2026-07-06

Media depth — cheap metadata, thumbnails, convert Shipped

Capability phase 2 landed end-to-end (tech-spec 04, 08). The cost-tiered media handlers now fill real attributes at scan: audio via a symphonia container probe (sample rate, channels, bit depth, duration, codec — no PCM decode), images via header dimensions + a PNG IHDR alpha/depth sniff, and 3D by hand-walking the GLB JSON chunk / glTF / OBJ / STL / PLY for vertex, triangle, mesh, material, texture, and rig/anim/UV counts — never decoding geometry or the BIN chunk (the cheap contract, §4). These persist to the per-type attribute tables and surface on the grid rows (key_attrs) and the Inspector. Server-rendered image thumbnails (downscaled PNG, content-hash-keyed on-disk cache) serve at GET /api/v1/assets/{id}/thumbnail, with audio waveforms and 3D turntables kept as the interactive WASM islands; the web grid/inspector render real previews with a graceful fall-back to the honest typed tile. The convert pipeline (CLI-first, 3dam convert) decodes via the same handlers and re-encodes non-destructively — image transcode/resize and audio→WAV — with dry-run planning, the source-safety invariant (never writes into a registered source), atomic temp-write-then-rename, and collision policy. Deeper codec and format coverage (DDS/KTX2, MP4/AAC decode, mesh optimise/compression, more encode targets) stages behind the same seams.

2026-07-06

Automation — analysis, similarity, dedup, review Shipped

Capability phase 3 — the differentiator — landed end-to-end (tech-spec 05). A new AnalysisRunner (3dam-core::analysis) runs the versioned Plan→Extract→Derive→Classify→Index→Dedup pipeline as a background job (3dam analyze, incremental via analysis_version; --force re-runs). Per image it derives the tileability metric (edge-continuity vs internal gradient + autocorrelation repeat-period, §6), a dHash perceptual hash, and dominant colours, and it emits auto-tag / auto-category suggestions that are written suggested, never confirmed. Each media type gets a normalised embedding in its own EmbeddingSpace (schema V3 embedding table); find_similar ranks neighbours by cosine (brute-force exact in v1) and composes with the same facet filters as search. Duplicate review surfaces exact (content-hash) and near (embedding-cosine, union-find) groups with a suggested keep — grouping only, never deletion. The accept/reject suggestion lifecycle (3dam tag <id> <name> [--reject]) promotes/negates tags reversibly and a reject survives re-analysis. All four surfaces ride the LibraryService seam — embedded and remote (--connect) return identical results. Model-free v1 per ADR 0006: the default build runs offline with no weights, behind the exact seam the SigLIP/CLAP path plugs into as a model_version bump; the web review UX and HNSW-at-scale index are named follow-ups.

2026-07-06

Reach — network sources, watch, smart folders, export Shipped

Capability phase 4 landed end-to-end (tech-spec 07). The FileSource seam was generalised: every source resolves an entry's bytes to a local path via fetch (in place for local, a downloaded temp file suffixed with the logical extension for remote), and a SourceConnection model + open_source factory rebuild the backend from the persisted connection blob (secret held server-side; clients only ever see the sanitised URI). Two real network backends ride that seam: SFTP via russh + russh-sftp and SMB2/3 via the pure-Rust smb crate, driven from a private current-thread runtime because the scan runs off the async workers. Unreachable hosts/bad creds mark the source offline and are skipped, never fatal (fail-soft). Delta re-scan compares each entry's size+mtime change token and only re-opens changed files, marking vanished ones absent (non-destructive). Watch/auto-rescan uses OS change notification for local sources (debounced) and polling for remote, each triggering a delta scan. Smart folders resolve a saved query live; manual collections hold an explicit set, surfaced on the inspector record. Export/manifests emit JSON, CSV, or per-asset JSON sidecars over a selector (ids / collection / query / whole library), with an attribution-only credits mode. All CLI-first (sources add sftp://…|smb://…, scan --delta, collections …, export …) over the LibraryService seam — embedded and --connect return identical results. Remote-source analysis/convert (fetch-through) and the web-client surfaces for collections/export are named follow-ups; the desktop GUI stays phase 5.

2026-07-06

Server & web — feature flags, basic auth, MCP Shipped

Capability phase 5's remaining half landed (tech-spec 10, 11, ADR 0003/0004) — the serve/--connect/web-client half shipped earlier. A server config store (server.db, separate from the library file) holds a versioned feature-flag table, token records, and an append-only audit log; the live flag state is seeded by a serve.toml config file (config_authority = seed-only) and thereafter owned by the admin surface. Three flags gate real surfaces — authentication (off/anonymous/token), mcp_server (off/read-only/read-write), network_writes — each live-toggleable, with optimistic-concurrency versioning and a server-side confirm-on-exposure gate. Basic access control resolves every request to an AuthContext + scope set through one auth layer over the whole surface (API, admin, MCP); Off grants the localhost owner full trust, Token requires a bearer key, and read/write/admin scopes gate handlers (writes further gated by the network ceiling beyond localhost). Bearer API tokens are issued through the audited admin API (secret shown once, blake3-hashed at rest). The admin API (/admin/api/*) is the single source of truth driven by both the CLI (3dam admin flags|flag|token|status|audit, embedded or --connect) and the web Settings / Administration surface (grouped flag cards, warn-and-confirm, token management, audit trail). The MCP server (ADR 0003, hand-rolled JSON-RPC over dyn LibraryService — no subprocess) serves tools/resources/prompts over both 3dam mcp stdio (locally trusted) and POST /mcp on the shared port; the mcp_server flag mounts/unmounts it (Off ⇒ 404) and a WriteGate (bind + flag + caller scope) filters the write tools. Binding beyond localhost without TLS is refused unless --insecure (ADR 0009 §4). User accounts, sessions, OIDC, and TLS layer on the same AuthContext seam in phase 6.

Mobile & tablet posture

Desktop/tablet-first; phones are graceful-degrade, not a separate product. Because the web client is DOM-based this is cheap:

  • Collapse the three-region workspace to a single scrollable column at tablet width.
  • 44×44px minimum touch targets; touch-action: manipulation on canvas overlay controls.
  • Stack side-by-side panes (e.g. viewer + detail) vertically with viewport-unit heights and a min-height floor so the 3D canvas stays usable.
  • Treat full small-screen polish and real-device testing as tracked UX debt, not a v1 gate.

Release & distribution

The canonical release plan lives in tech-spec 15 §15.5 (implementable CI detail); the scaffold is at .github/workflows/release.yml. In brief, following the pattern proven in the sibling mogen project:

  • Trigger: push a v* tag (plus manual workflow_dispatch); contents: write to cut the release.
  • Build matrix (fail-fast: false): Linux (x86_64-unknown-linux-gnu), macOS (Intel + aarch64), Windows (x86_64-pc-windows-msvc).
  • Web client first. A release builds the React web client and embeds its static assets into the 3dam binary (rust-embed) before cargo build, so one binary serves the web UI with no separate deploy — then a single cargo build -p 3dam --release --locked --target <triple>.
  • Per-OS packaging: Linux tar.gz + .deb (cargo-deb); Windows .zip + .msi (cargo-wix); macOS .app in a .dmg. Publish collects artifacts, generates SHA256SUMS, creates the release.
  • v1 decisions: unsigned (accept Gatekeeper/SmartScreen warnings); GitHub Releases is the sole v1 channel (Homebrew tap + cargo-binstall fast-follow) — ADR 0009 §10.
